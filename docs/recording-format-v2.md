# gpumon 記錄檔格式 (版本 2)

GUI 經由 SSH 執行遠端程式, 把收到的監看資料存成記錄檔, 歷史畫面由記錄檔讀取. 與記錄檔有關的遠端訊息有三種. devices 訊息為連線後的第一則訊息, 列出各 GPU 的資訊; sample 訊息於每次取樣送出, 含各 GPU 的數值與程序列表; error 訊息回報遠端發生的錯誤. 本文件定義記錄檔格式的版本 2. 記錄檔由三部分依序組成, 三者之間沒有填充位元組:

- 固定區 (第 3 章), 識別檔案, 格式版本與說明區的長度.
- 說明區 (第 3 章), 以 JSON 記錄主機與各 GPU 的資訊.
- 記錄區 (第 4 章), 由一連串區塊組成, 區塊內存放取樣, 程序列表與事件的記錄 (第 5 章).

讀取規則見第 6 章, 版本 1 檔案的處理見第 7 章.

## 1. 需求

- **附加寫入.** 連線期間只在檔尾附加, 已寫入的內容不再修改. 程式異常結束時, 只遺失尚未存檔的記錄.
- **依時刻定位.** 讀取端不必從檔頭依序讀取即可找到任一時刻的資料, 也可以由任一處往前讀.
- **損壞範圍有限.** 檔案中段損壞時, 只失去損壞的區塊, 以及其後至下一個列表重設區塊 (見 4.3) 為止的程序列表.
- **不損失資訊.** 每次取樣的 GPU 數值, GPU 程序列表與 CPU 程序列表皆完整保存, 不降低記錄頻率, 不捨棄程序, 欄位或文字.
- **縮小檔案.** 程序列表只寫入與前一次取樣不同的程序與欄位, 並壓縮每個區塊.
- **可擴充.** 新增記錄種類或欄位不必提高格式版本, 讀取端略過不認得的部分.

## 2. 通則

- 多位元組整數一律為 little-endian, 文字一律為 UTF-8.
- 本文件的位移皆由 0 起算, 長度與位移的單位皆為位元組.
- 時刻一律為 Unix 時間的微秒數, 以本機時鐘為準.
- 取樣記錄與錯誤記錄的時刻依所屬連線的時間基準計算, 公式如下, `round` 為四捨五入至最接近的整數:

  ```
  t_base + round((ts - ts_base) * 1000000)
  ```

  `ts` 為遠端訊息所帶的時間戳記. `t_base` 與 `ts_base` 依序為本機收到該次連線第一筆 sample 訊息的時刻與該筆的 `ts`. 檔案第一次連線的時間基準即說明區的 `t_wall_0` 與 `ts_0`; 自動重新連線後的時間基準不存入檔案.
- 記錄依寫入的先後排列, 時刻不遞減. 算出的時刻早於前一筆記錄的時刻時, 以前一筆記錄的時刻計.

**存放位置與檔名**

- 記錄檔位於應用程式資料目錄下的 `history/<主機目錄>/`.
- `<主機目錄>` 由主機識別 (`user@addr`, 連接埠不是 22 時為 `user@addr:port`) 換算而得. 連接埠前的 `:` 換成 `+`, 再把不屬於英文字母, 數字, `.`, `_`, `@`, `-` 與該 `+` 的字元逐一換成 `_`. 換算結果為空字串或只由 `.` 組成時不建立記錄檔.
- 檔名為 `<YYYYMMDD-HHMMSS>.gpurec`, 日期與時間為說明區 `t_wall_0` 換算成本機時區後的值. 同名檔案已存在時, 於 `.gpurec` 之前依序加上 `-2`, `-3`, 直到不重複為止.

## 3. 固定區與說明區

固定區位於檔案位移 0, 長度為 16, 配置如下:

| 位移 | 長度 | 型別 | 內容 |
|---|---|---|---|
| 0 | 8 | 位元組 | 識別字串, 固定為 ASCII 字元 `GPUMONRC` |
| 8 | 2 | uint16 | 格式版本, 本文件所述格式的值為 2 |
| 10 | 2 | uint16 | GPU 張數, 以下稱 N, 等於 devices 訊息 `gpus` 陣列的元素個數 |
| 12 | 4 | uint32 | 說明區的長度, 以下稱 M |

N 為 0 時不建立記錄檔.

說明區位於檔案位移 16, 長度為 M, 內容為一個 JSON 物件, 結尾不含換行. 成員如下:

| 成員 | JSON 型別 | 內容 |
|---|---|---|
| `host` | 字串 | 該主機的識別 |
| `t_wall_0` | 整數 | 本機收到該檔案第一次連線第一筆 sample 訊息的時刻 |
| `ts_0` | 數值 | 該筆 sample 訊息的 `ts` 原值 |
| `devices` | 物件 | 該檔案第一次連線收到的 devices 訊息, 所有成員原樣存入 |

- 說明區於建立檔案時寫入. 變更主機識別時, 程式以新的說明區另寫一份檔案, 記錄區原樣複製; 因此 M 可能改變, 記錄區內的位置一律以記錄區的起點起算.
- 讀取時略過說明區中不認得的成員.

## 4. 記錄區與區塊

記錄區自檔案位移 `16 + M` 起延伸到檔尾, 由一連串區塊組成. 寫入端每次存檔寫入一個區塊, 下稱 **區塊**. 本章所稱的 "記錄區內的位移" 為檔案位移減去 `16 + M`.

### 4.1 區塊開頭

每個區塊由長度固定為 56 的區塊開頭與長度不定的區塊內容組成. 區塊開頭的配置如下:

| 位移 | 長度 | 型別 | 內容 |
|---|---|---|---|
| 0 | 16 | 位元組 | 同步標記 (sync marker), 固定為十六進位 `6B C6 6F F3 FA 80 24 0F 68 2B E4 FB 0C 08 36 BB` |
| 16 | 4 | uint32 | 區塊內容的長度, 以下稱 C |
| 20 | 4 | uint32 | 區塊內容解壓縮後的長度 |
| 24 | 4 | uint32 | 前一個區塊的總長度, 即 56 加上前一個區塊的 C; 第一個區塊為 0 |
| 28 | 8 | int64 | 區塊內第一筆記錄的時刻 |
| 36 | 8 | int64 | 區塊內最後一筆記錄的時刻 |
| 44 | 8 | uint64 | 最近的列表重設區塊 (見 4.3) 於記錄區內的位移; 本區塊即為列表重設區塊時為本區塊的位移 |
| 52 | 4 | uint32 | 校驗碼 (checksum), 為 CRC-32C (Castagnoli 多項式), 計算範圍為本區塊位移 0 至 51 與整個區塊內容 |

讀取端以同步標記在檔案中找出區塊的起點, 以校驗碼判斷區塊是否完好.

### 4.2 區塊內容

區塊內容為一個 zstd frame. 解壓縮後為一連串記錄, 每筆記錄為一個 varint 編碼的長度, 其後緊接該長度的 protobuf 訊息, 訊息的定義見 5.1. 記錄依寫入的先後排列.

### 4.3 列表重設區塊

程序列表只寫入與前一次取樣的差異 (見 5.4). 寫入端在部分區塊的起點把比較對象重設為空列表, 這些區塊下稱 **列表重設區塊**. 讀取端由最近的列表重設區塊依序套用差異, 即可還原任一次取樣的程序列表.

- 檔案的第一個區塊為列表重設區塊.
- 之後的區塊, 其第一筆記錄的時刻距上一個列表重設區塊第一筆記錄的時刻達 10 分鐘以上時, 寫成列表重設區塊.
- 讀取端只依區塊開頭位移 44 的欄位找出列表重設區塊, 不依賴 10 分鐘這個數值; 調整此間隔不必變更格式版本.

### 4.4 寫入

- 寫入端於下列時機存檔:
  - 連線期間每 5 秒一次.
  - 判定非預期斷線時.
  - 主機轉為未連線時.
- 每次存檔把尚未存檔的記錄寫成一個區塊, 以一次附加寫入檔尾. 沒有尚未存檔的記錄時不寫入區塊.
- 同一筆 sample 訊息產生的取樣記錄與程序變動記錄寫入同一個區塊.
- 附加中途失敗時, 把檔案截回附加之前的長度, 記錄保留於記憶體, 於下次存檔時連同新的記錄寫成一個區塊. 檔尾不留下不完整的區塊.

## 5. 記錄

### 5.1 記錄的共同結構

每筆記錄為一個 `Record` 訊息. `Record` 帶有時刻, 並以 protobuf 的 oneof 存放下列五種內容之一:

| 編號 | 名稱 | 型別 | 內容 |
|---|---|---|---|
| 1 | `time` | int64 | 時刻 |
| 2 | `sample` | `Sample` | 取樣記錄, 見 5.2 |
| 3 | `error` | `Text` | 錯誤記錄, 見 5.3 |
| 4 | `disconnect` | `Text` | 斷線記錄, 見 5.3 |
| 5 | `gpu_procs` | `GPUProcChanges` | GPU 程序變動記錄, 見 5.5 |
| 6 | `cpu_procs` | `CPUProcChanges` | CPU 程序變動記錄, 見 5.6 |

- protobuf 解碼時把不認得的欄位編號保留為未知欄位, 不視為錯誤. 讀取端遇到 oneof 未設定的記錄即略過該筆, 因此新增的記錄種類不影響舊版讀取端.
- 本章標為 optional 的欄位使用 protobuf 的 `optional`, 讀取端可區分 "無值" 與 "值為 0". 型別為訊息的欄位本身即可區分有無值.
- 數值與文字皆依原值存入, 不截斷, 不限制範圍.
- 未標 optional 的整數, bool 與 string 欄位, 值為 0, 假或空字串時寫入端省略該欄位, 讀取端以該值解讀.
- repeated 的整數欄位 (`cleared`) 以 packed 編碼寫入. 讀取端 packed 與逐一編碼皆接受.

### 5.2 取樣記錄

本機每收到一筆 sample 訊息, 寫入一筆取樣記錄. 時刻依第 2 章的公式計算, 其中 `ts` 為該筆 sample 訊息的 `ts`.

`Sample` 的欄位如下:

| 編號 | 名稱 | 型別 | 內容 |
|---|---|---|---|
| 1 | `interval_ms` | uint32 | 該次取樣當時遠端程式的取樣間隔, 單位為毫秒 |
| 2 | `gpus` | repeated `GPUValues` | N 個元素, 第 i 個元素對應說明區 `devices.gpus` 陣列的第 i 個元素 |

sample 訊息內的 GPU 以 `id` 與 `devices.gpus` 元素的 `id` 配對. sample 訊息中沒有某張 GPU 時, 其對應元素的所有欄位皆無值.

`GPUValues` 的欄位如下, 皆為 optional, 取自 sample 訊息中該 GPU 的同名欄位; 該欄位被省略時無值:

| 編號 | 名稱 | 型別 | 內容 |
|---|---|---|---|
| 1 | `util` | int64 | 使用率, 百分比 |
| 2 | `fan` | int64 | 風扇轉速, 百分比 |
| 3 | `enc` | int64 | 編碼器使用率, 百分比 |
| 4 | `dec` | int64 | 解碼器使用率, 百分比 |
| 5 | `temp` | sint64 | 溫度, 攝氏度 |
| 6 | `power_w` | int64 | 功耗, 瓦 |
| 7 | `clock_gpu` | int64 | GPU 時脈, MHz |
| 8 | `clock_mem` | int64 | 記憶體時脈, MHz |
| 9 | `mem_used` | uint64 | 記憶體用量, 位元組 |

### 5.3 錯誤記錄與斷線記錄

錯誤記錄與斷線記錄的內容皆為 `Text`, 其唯一欄位為編號 1 的 `text`, 型別為 string.

- 本機每收到一則 error 訊息, 寫入一筆錯誤記錄. 時刻依第 2 章的公式計算, 其中 `ts` 為該則 error 訊息的 `ts`. `text` 為 error 訊息的 `msg`. 該次連線第一筆 sample 訊息之前收到的 error 訊息不存入記錄檔.
- 自動重新連線成功並接續寫入原記錄檔時, 本機於該次連線第一筆取樣記錄之前寫入一筆斷線記錄. 時刻為本機判定斷線的時刻. `text` 為 GUI 判定的斷線原因, 一律為英文.

### 5.4 程序變動記錄的共同規則

程序列表分為 GPU 程序列表與 CPU 程序列表兩種. 本機每收到一筆 sample 訊息, 分別把兩種列表與同種類前一次取樣的列表比較; 有差異的種類寫入一筆該種類的程序變動記錄, 沒有差異的種類不寫入. 程序變動記錄的時刻與同一筆 sample 訊息的取樣記錄相同, 寫於該取樣記錄之後.

比較時以識別欄位配對兩份列表中的程序, 依下列規則寫入:

- 新出現的程序, 寫入識別欄位與所有有值的欄位.
- 兩份列表皆有的程序, 寫入識別欄位與值改變的欄位; 由有值變為無值的欄位, 把其欄位編號寫入 `cleared`. 沒有任何欄位改變的程序不寫入.
- 只在前一次取樣列表中的程序, 寫入識別欄位, 並將 `ended` 設為真.

比較對象另有兩項規則:

- 寫入端寫入列表重設區塊時, 把兩種列表的比較對象設為空列表. 此後每種列表的下一次比較以空列表為對象, 不論該次比較位於此區塊或之後的區塊.
- 斷線記錄不重設比較對象. 斷線前後的累計值能否相減, 屬於使用率計算的規則, 與本格式無關.

文字欄位以完整內容比較. 型別為 `EngineValues` 的欄位有任一鍵或值不同時, 視為整個欄位改變, 寫入完整內容.

遠端回報的程序元素依下列規則轉為程序列表:

- 不是 JSON 物件, 或沒有整數識別欄位的元素, 不列入程序列表, 同一次取樣的其他程序照常處理.
- 同一次取樣中識別欄位相同的程序, 只取第一個.
- 成員的值為 null, 或型別與同名欄位不符時, 該成員存入 `extra`.
- `extra` 的成員依鍵的字典序排列, 不含多餘的空白. 成員相同的 `extra` 因此文字相同, 可直接比較.

### 5.5 GPU 程序變動記錄

GPU 程序列表為 sample 訊息內各 GPU 的 `procs` 合併而成. `GPUProcChanges` 的唯一欄位為編號 1 的 `procs`, 型別為 repeated `GPUProc`, 每個元素為一個程序的變動.

GPU 程序以 GPU 的 `id` 加上程序編號識別. 遠端回報的程序資料沒有啟動時刻; 程序編號被新程序重用時, 依 5.4 的規則寫入其改變的欄位.

`GPUProc` 的欄位如下:

| 編號 | 名稱 | 型別 | 內容 |
|---|---|---|---|
| 1 | `gpu` | int64 | 識別欄位, 該程序所在 GPU 的 `id` |
| 2 | `pid` | int64 | 識別欄位, 程序編號 |
| 3 | `ended` | bool | 該程序已不在列表中 |
| 4 | `user` | optional string | 使用者帳號名稱 |
| 5 | `mem` | optional uint64 | 該程序的 GPU 記憶體用量, 位元組 |
| 6 | `util` | optional int64 | 該程序的 GPU 使用率, 百分比 |
| 7 | `cmd` | optional string | 指令列 |
| 8 | `engines` | `EngineValues` | 各引擎的累計忙碌時間, 奈秒 |
| 9 | `engine_capacity` | `EngineValues` | 各類引擎的數量 |
| 10 | `cycles` | `EngineValues` | 各引擎的累計週期數 |
| 11 | `total_cycles` | `EngineValues` | 各引擎的累計總週期數 |
| 12 | `extra` | optional string | `procs` 元素中上列以外的成員, 以 JSON 物件文字存放; 沒有這類成員時無值 |
| 13 | `cleared` | repeated uint32 | 由有值變為無值的欄位編號, 只會是 4 至 12 |

編號 4 至 12 的欄位取自 `procs` 元素的同名成員, `extra` 除外. `EngineValues` 的唯一欄位為編號 1 的 `values`, 型別為 map<string, uint64>, 鍵為引擎名稱.

### 5.6 CPU 程序變動記錄

CPU 程序列表為遠端主機上的所有程序. `CPUProcChanges` 的唯一欄位為編號 1 的 `procs`, 型別為 repeated `CPUProc`.

CPU 程序以程序編號加上啟動時刻識別, 避免程序編號被重用時把兩個程序視為同一個. 遠端程式回報 CPU 程序時, 每個程序須提供這兩個值.

`CPUProc` 的欄位如下:

| 編號 | 名稱 | 型別 | 內容 |
|---|---|---|---|
| 1 | `pid` | int64 | 識別欄位, 程序編號 |
| 2 | `start_time` | int64 | 識別欄位, 遠端回報的程序啟動時刻原值, 只用於識別 |
| 3 | `ended` | bool | 該程序已不在列表中 |
| 4 | `ppid` | optional int64 | 父程序編號 |
| 5 | `user` | optional string | 使用者帳號名稱 |
| 6 | `cmd` | optional string | 指令列 |
| 7 | `cpu_time_ms` | optional uint64 | 累計 CPU 時間, 毫秒 |
| 8 | `mem` | optional uint64 | 常駐記憶體用量, 位元組 |
| 9 | `extra` | optional string | 遠端回報的上列以外的成員, 以 JSON 物件文字存放; 沒有這類成員時無值 |
| 10 | `cleared` | repeated uint32 | 由有值變為無值的欄位編號, 只會是 4 至 9 |

## 6. 讀取

### 6.1 有效區塊與區塊間的移動

同時符合下列條件的區塊為有效區塊:

- 同步標記相符.
- 區塊開頭與區塊內容皆完整位於檔案內.
- 校驗碼相符.

由一個有效區塊移到相鄰的區塊時, 下一個區塊位於本區塊的位置加上 56 與 C, 前一個區塊位於本區塊的位置減去位移 24 所記的長度.

### 6.2 檔案的起訖

- 第一個區塊位於記錄區的起點.
- 讀取端由檔尾往前搜尋同步標記, 找到的第一個有效區塊即最後一個有效區塊. 其後的部分為寫入中或異常結束時留下的內容, 讀取時略過.
- 檔案的起訖時刻為第一個有效區塊的第一筆記錄時刻, 與最後一個有效區塊的最後一筆記錄時刻.

### 6.3 依時刻定位

讀取端在記錄區內任選一個位置, 往後搜尋同步標記, 找到有效區塊後讀取其位移 28 與 36 的時刻. 以此方式對位置做二分搜尋 (binary search), 即可找到含有某時刻的區塊. 要找某時刻之前最近的一筆取樣時, 由該區塊往前讀.

### 6.4 損壞的區塊

往後讀取時遇到無效區塊, 由其起點之後搜尋下一個同步標記, 從找到的有效區塊繼續讀取. 往前讀取時遇到無效區塊, 由其起點往前搜尋同步標記, 從找到的有效區塊繼續讀取. 有效區塊的內容解壓縮失敗, 或解壓縮後的長度與位移 20 所記不符時, 讀取該區塊的記錄時視同無效區塊. 損壞的影響如下:

- 損壞區塊內的記錄全部遺失.
- 損壞區塊之後至下一個列表重設區塊之前, 程序列表無法還原, 讀取端視為沒有程序列表.
- 其他區塊的取樣, 錯誤與斷線記錄不受影響.

### 6.5 還原某次取樣的程序列表

某次取樣的程序列表依下列步驟還原, GPU 與 CPU 程序列表各自進行:

1. 由該次取樣記錄所在區塊之區塊開頭位移 44 的欄位, 找到最近的列表重設區塊.
2. 以空列表為起點, 自列表重設區塊起依序套用同種類的程序變動記錄. 套用至下列位置之前為止, 以先到者為準: 該次取樣記錄之後的下一筆取樣記錄, 下一個列表重設區塊, 下一個無效區塊, 檔尾. 同一筆 sample 訊息的程序變動記錄與其取樣記錄位於同一區塊 (見 4.4), 因此在區塊邊界停止不會遺漏. 套用時, 新程序加入列表, 已有的程序以記錄中的欄位取代原值, `cleared` 所列的欄位改為無值, `ended` 為真的程序自列表移除.
3. 列表重設區塊至該次取樣之間有無效區塊時, 該次取樣沒有程序列表.

計算使用率所需的前一次取樣列表, 以同樣方式取得.

## 7. 格式版本

- 本機只建立版本 2 的記錄檔.
- 版本 1 的記錄檔只供讀取, 不再附加記錄. 變更主機識別而另寫檔案時, 維持該檔案原本的版本.
- 兩個版本的固定區配置相同. 讀取端依位移 8 的格式版本選擇讀取方式; 識別字串不符者不是記錄檔, 格式版本為其他值時拒絕開啟, 並顯示該版本號.
